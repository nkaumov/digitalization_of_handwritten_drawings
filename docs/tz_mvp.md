# ТЗ на MVP-систему цифровизации рукописных чертежей

## 1. Назначение системы

Система предназначена для перевода рукописных чертежей помещений в цифровой редактируемый чертеж.

На входе система получает фотографию или изображение рукописного чертежа.
На выходе система формирует цифровую схему, которая автоматически открывается во встроенном редакторе и может быть отредактирована пользователем.

В первой версии акцент делается на распознавании:
- прямых линий;
- замкнутых контуров;
- нескольких контуров на одном изображении;
- текстовых размеров сторон;
- соединений между линиями.

Система должна быть изначально спроектирована модульно, с расширяемой hook-архитектурой, чтобы позже без ломки ядра можно было добавлять новые элементы: трубы, бруски, вырезы, внутренние элементы, дополнительные типы геометрии, площади, периметры, экспортные форматы и т.д.

---

## 2. Цель MVP

Цель MVP — получить рабочую систему, которая:
1. создает пустой чертеж или чертеж по фотографии;
2. распознает на фото прямолинейные контуры и размеры;
3. собирает цифровую геометрию из распознанных данных;
4. автоматически открывает результат в редакторе;
5. позволяет пользователю вручную исправлять линии, узлы и размеры;
6. сохраняет чертеж в базе как внутреннюю сущность системы;
7. экспортирует результат пользователю в PDF или изображение.

Важно: в MVP допускается, что распознавание не идеально. Критерием успеха является не полная магия без правок, а корректная сборка цифрового чертежа, который можно быстро дотянуть в редакторе.

---

## 3. Границы MVP

### 3.1. Что входит в MVP
- Создание нового файла двумя способами:
  - пустой лист;
  - генерация по фотографии.
- Веб-редактор с сеткой.
- Работа с точками и прямыми сегментами.
- Поддержка нескольких замкнутых контуров на одном входном изображении.
- Распознавание числовых размеров сторон.
- Привязка размеров к сегментам.
- Ручное редактирование:
  - перемещение точек;
  - изменение длины подписи;
  - удаление линий;
  - добавление линий;
  - соединение линий;
  - корректировка контуров.
- Автосоздание цифрового чертежа после анализа изображения.
- Сохранение чертежа в БД.
- Экспорт в PDF / изображение.
- Служебная фиксация промежуточных этапов распознавания для дебага.

### 3.2. Что не входит в MVP
- Дуги, кривые, окружности и сложная нелинейная геометрия.
- Внутренние вырезы, отверстия, сложные вложенные контуры как обязательная функция.
- Автоматический расчет площади и периметра как обязательная часть.
- Пользовательский импорт/экспорт внутреннего JSON-файла через интерфейс.
- Публичная система внешних модулей установки.
- Полноценный CAD-уровень редактирования.
- Гарантия 100% распознавания в любом качестве входа.

## 4. Базовые продуктовые сценарии

### 4.1. Создание пустого чертежа
1. Пользователь нажимает "+".
2. В модальном окне выбирает вариант "Пустой".
3. Открывается пустой редактор с сеткой и боковой панелью инструментов.
4. Пользователь строит чертеж вручную.
5. При сохранении данные попадают в БД.

### 4.2. Создание чертежа по фотографии
1. Пользователь нажимает "+".
2. В модальном окне выбирает вариант "Сгенерировать по фото".
3. Создается новый пустой чертеж.
4. Открывается модальное окно загрузки изображения.
5. Пользователь загружает фото.
6. Сервис распознавания анализирует фото.
7. Результат автоматически импортируется во внутреннюю модель чертежа.
8. Пользователь видит цифровой чертеж в редакторе.
9. При необходимости вручную правит линии и размеры.
10. Нажимает сохранить.

## 5. Основные принципы проектирования

### 5.1. Модульность как базовое требование
Все части системы должны быть разложены на мелкие независимые модули.
Запрещается строить крупные монолитные файлы с большой смешанной логикой.

### 5.2. Расширение через hook-архитектуру
Расширение системы должно выполняться через внутренние хуки и расширяемые точки подключения.
Это нужно для:
- безопасного добавления новых типов элементов;
- быстрой отладки;
- предсказуемого расширения пайплайна;
- уменьшения риска поломок при доработках.

### 5.3. Отделение редактора от AI-пайплайна
Редактор и сервис распознавания должны быть изолированы логически и технически.
AI-часть должна работать как отдельный сервис, который получает входные данные, выполняет многошаговую обработку и возвращает нормализованный результат.

### 5.4. Внутренний формат важнее внешних файлов
Пользователь не должен работать с JSON-файлами напрямую.
Внутренний контракт должен существовать для системы, но не обязан быть частью пользовательского интерфейса.

## 6. Функциональные требования

### 6.1. Редактор
Редактор должен поддерживать:
- отображение сетки;
- отображение линий и узлов;
- работу с несколькими контурами;
- отображение подписей размеров;
- панорамирование;
- зум экрана;
- базовый масштабный режим;
- выделение элементов;
- перемещение точек;
- добавление сегментов;
- удаление сегментов;
- ручное соединение линий;
- сохранение изменений.

### 6.2. Геометрия
Система должна поддерживать:
- точки;
- прямые сегменты;
- цепочки сегментов;
- замкнутые контуры;
- несколько контуров в одном чертеже;
- числовые размеры, привязанные к сегментам.

### 6.3. Импорт из фото
Система должна:
- принимать изображение;
- сохранять исходный файл;
- проводить обработку изображения;
- распознавать линии;
- распознавать числовые подписи размеров;
- пытаться определить соответствие чисел сегментам;
- строить цифровую геометрию;
- отдавать результат в редактор.

### 6.4. Обработка ошибок распознавания
Если часть данных распознана неуверенно, система должна:
- сохранить результат в максимально пригодном виде;
- зафиксировать warning;
- пометить спорные места внутри служебной модели;
- позволить пользователю исправить результат вручную.

### 6.5. Единицы измерения
В MVP вводится следующая логика:
- основной акцент делается на реальные размеры, указанные на рисунке;
- геометрия должна по возможности строиться на основе распознанных длин, а не по визуальной длине рукописных линий;
- базовая единица хранения внутри системы — `мм`;
- если на чертеже явно не указаны единицы измерения, система пытается нормализовать значения к общей логике контура;
- если на чертеже смешаны форматы записи (`450` и `2,7`), система должна попытаться привести их к согласованному виду;
- если полная согласованность невозможна, результат сохраняется как есть, а пользователь корректирует его в редакторе.

### 6.6. Масштабы
В системе должны быть разделены два вида масштаба:

1. **Масштаб представления данных** — связь между реальными размерами чертежа и отображением на рабочем поле.
2. **Экранный зум** — приближение и отдаление интерфейса без изменения самих данных.

На MVP допускается упрощение:
- реальные размеры хранятся отдельно;
- визуальный размер сегмента в редакторе вычисляется из внутренней модели;
- изменение числовой длины в MVP не обязано автоматически перестраивать всю геометрию идеально;
- визуально чертеж должен быть максимально приближен к распознанной форме.

## 7. Нефункциональные требования

- Система должна быть полностью локально запускаемой.
- Настройки окружения должны задаваться через `.env`.
- Все пользовательские тексты должны быть вынесены в i18n.
- Система должна быть готова минимум к двум языкам.
- Код должен быть разделен по доменам и слоям.
- Не допускается хранение текстов интерфейса inline в компонентах.
- Все API-контракты должны быть типизированы.
- Вся критичная логика должна покрываться тестами.

## 8. Архитектура решения

## 8.1. Общая схема
Система состоит из трех основных частей:

1. **Frontend Editor** — веб-интерфейс редактора.
2. **Backend API** — основной сервер приложения.
3. **AI Recognition Service** — отдельный Python-сервис распознавания.

### 8.2. Логика взаимодействия
- Frontend общается с Backend API.
- Backend хранит проекты, чертежи, результаты и статус обработки.
- Backend передает изображение в AI-сервис.
- AI-сервис выполняет пайплайн анализа.
- AI-сервис возвращает структурированный результат.
- Backend сохраняет результат и отдает его редактору.

## 12. Правила принятия решений по размерам

### 12.1. Общий принцип
Система должна стремиться построить геометрию по числовым размерам, а не по фактической длине штриха на фото.

### 12.2. Порядок приоритета
При конфликте интерпретаций применяются следующие приоритеты:
1. геометрическая согласованность контура;
2. наиболее вероятное чтение OCR/vision;
3. возможность ручной корректировки пользователем.

### 12.3. Смешение форматов записи
Если на одном изображении встречаются записи вроде `450` и `2,7`, система должна:
1. сохранить исходный `raw_text`;
2. попытаться определить предполагаемую единицу;
3. попытаться привести значения к единой системе;
4. если уверенность низкая — пометить warning и не блокировать открытие результата в редакторе.

8. Привязка размеров к сегментам.
9. Нормализация единиц.
10. Сборка внутреннего результата.
11. Формирование debug-данных.

### 13.2. Требования к пайплайну
- Каждая стадия должна быть изолируемой.
- Каждая стадия должна логироваться.
- Для каждой стадии должна быть возможность подмены реализации.
- Каждая стадия должна иметь входной и выходной контракт.

### 14.1. Общие правила
Хуки являются внутренним механизмом расширения и не предполагают установку внешних модулей пользователем.

Каждый домен должен иметь:

## 16. Хранение промежуточных результатов

Для удобства отладки система должна уметь сохранять:
- исходное изображение;
- нормализованное изображение;
- найденные линии;
- найденные текстовые блоки;
- сырые OCR-результаты;
- собранные контуры;
- итоговый внутренний payload;
- warnings и confidence.

Промежуточные данные не обязаны показываться пользователю, но должны быть доступны разработчику.

## 17. UX-требования к загрузке изображения

При загрузке фото пользователь должен видеть инструкцию, где указано:
- фото нужно делать без сильного наклона;
- линии должны быть четко видны;
- у каждой стороны желательно должна быть проставлена длина;
- записи размеров должны быть в одном формате;
- текст должен быть читаемым;
- желательно избегать теней и сильных бликов.

## 19. Приоритеты реализации

### Высокий приоритет
- модульность;
- внутренний контракт;
- рабочий редактор;
- распознавание прямых линий;
- сборка нескольких контуров;
- распознавание размеров;
- автооткрытие результата в редакторе;
- ручная правка.

### Средний приоритет
- улучшение алгоритма определения единиц;
- улучшение UX загрузки;
- красивый экспорт.

### Низкий приоритет для MVP
- площади и периметры;
- трубы;
- бруски;
- дуги;
- пользовательские импорты/экспорты внутренних форматов.

---

## 20. Критерии успеха MVP

MVP считается успешным, если:
- система локально запускается целиком;
- можно создать пустой чертеж;
- можно создать чертеж по фото;
- по типовым входным изображениям система собирает цифровой чертеж;
- распознанный результат автоматически открывается в редакторе;
- пользователь может исправить ошибки вручную;
- чертеж можно сохранить и экспортировать.

Не является обязательным критерием MVP:
- 100% автоматическое распознавание без правок;
- поддержка любых неаккуратных фото;
- поддержка всех возможных элементов чертежа.

---

## 21. Дальнейшее развитие после MVP

После MVP модульно могут быть добавлены:
- трубы;
- бруски;
- внутренние вырезы;
- сложные фигуры;
- площади и периметры;
- дополнительные типы геометрических элементов;
- более продвинутая логика согласования размеров;
- более точные AI-модели;
- серверное развертывание;
- интеграция с внешним модулем-открывателем.

---

## 22. Итоговое техническое решение MVP

Для MVP рекомендуется следующая схема:
- редактор: React + TypeScript + SVG;
- backend: Node.js + TypeScript;
- AI-сервис: Python + FastAPI;
- СУБД PHPMyAdmin
- БД: MySQL;
- архитектура: модульная, доменная, hook-based;
- основной результат для пользователя: редактируемый цифровой чертеж, открывающийся автоматически после анализа фото.

Это решение лучше всего соответствует текущему видению продукта: сначала дать рабочую цифровизацию рукописных чертежей, а затем без переписывания ядра расширять элементы и возможности системы.
